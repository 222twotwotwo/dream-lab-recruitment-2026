## 1. 项目概述

### 1.1 系统形态

- Web 网站，浏览器访问，响应式支持 PC / 平板 / 手机。
- 前后端分离：前端 Vue 3 + TypeScript，后端 Go，RESTful API + JSON。
- 视觉风格：白/浅灰背景、单一主色、圆角轻阴影、充足留白、信息层级清晰，减少装饰性元素与复杂动画。

### 1.2 建设目标

为实验室提供 **课题发布 → 模块拆分 → 学生报名 → 申请书评审 → 成员分配 → 任务进度跟踪 → 成果提交与展示 → 数据看板与报表** 的一体化管理平台，支撑课题运营决策。

### 1.3 范围与优先级总览

### 1.4 对标参考

参考开源之夏（OSPP）的信息架构：组织列表与主页、项目列表与筛选、学生注册与报名、多角色参与体系、帮助中心与活动流程时间线。

### 1.5 标准活动流程时间线

```
课题发布 → 报名开始 → 报名截止 → 申请书审核 → 项目开始
        → 任务执行（进度跟踪） → 成果提交与审核 → 项目结束/归档
```

## 2. 术语

| 术语 | 含义 |
| --- | --- |
| 课题 / 项目 | Project，一个可报名的研究课题，含若干模块 |
| 模块 | Module，课题内部的工作拆分单元，成员归属的最小单位 |

## 3. 用户角色与权限

### 3.1 角色定义

> 系统仅设 **普通用户** 与 **管理用户** 两种角色：用户角色管理、禁用用户、系统配置、操作日志、组织与标签管理均为管理用户职责。

| 角色 | 代码 | 说明 |
| --- | --- | --- |
| 未登录用户 | — | 只能访问公开内容，不能报名 |
| 普通用户（学生） | `USER` | 报名、提交申请书、参与课题、更新任务、提交成果 |
| 管理用户（导师/管理员） | `ADMIN` | 课题管理、模块管理、报名审核、成员分配、任务跟踪、成果审核、看板报表、**系统管理（用户/组织/标签/日志/系统配置）**、课题联系方式与入群二维码维护 |

**角色规则**

- 管理用户 **不开放自助注册**，由现有管理用户在后台创建或授权。
- 普通用户注册后默认角色 `USER`。
- 用户状态 `ACTIVE` / `DISABLED`，`DISABLED` 用户不可登录。
- **管理用户自保护规则（BR-24）**：系统内不存在更高权限角色，故以下约束为硬性要求，避免出现无人可管的系统：
  1. 管理用户 **不能禁用或删除自己**；操作自身角色/状态时返回 400。
  2. 系统必须始终保留 **至少 1 个 `ACTIVE` 管理用户**；最后一名管理用户不可被禁用、降级为 `USER` 或删除。
  3. 管理用户可互相禁用/降级，但上述两条硬约束优先，冲突时拒绝操作并提示原因。
  4. 管理用户的关键操作（创建/禁用用户、改角色、改系统配置）**全部写入操作日志**（BR-10）。
- **初始管理用户（BR-25）**：系统初始化时由部署脚本/环境变量种入首个管理用户账号，或在首次启动时进入一次性初始化向导创建；该账号无自助注册入口。

**数据权限（BR-02）**：所有管理用户权限完全一致、不分层，因此：

- 管理用户可查看并可管理 **全部课题与全部运营数据**（课题、模块、报名名单、申请书、成员、任务、成果、看板、报表）；
- `project.created_by` 仅作为 **责任人标识**，用于展示与"各管理用户负责课题数"等统计，**不作为权限边界**；
- 若日后需要按课题划分管理职责（权责分离），再引入独立的"课题负责人"维度（**已定稿：本期不做，见决策 D2**）；
- 普通用户仅可查看个人统计数据，不可进入看板与报表。

### 4.6 报名审核流（申请书提交与评审）

#### 4.6.1 申请书提交（学生）

**触发条件**：课题 `need_review = true` 时，报名必须提交申请书。

**字段**：个人陈述（必填，富文本，500~3000 字可配置）、对课题的理解（必填）、实施计划与时间安排（必填）、相关经历与技能（选填）、附件（选填）、关联简历（可选，从个人主页选择）。

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| REQ-APP-01 | 报名截止前可保存草稿 | P0 |
| REQ-APP-02 | 报名截止前可修改并重新提交，状态为"待评审" | P0 |
| REQ-APP-03 | 报名截止后申请书自动锁定（`locked_at`），不可修改 | P0 |
| REQ-APP-04 | 锁定需由定时任务或首次读取时惰性判定，保证与报名截止时间一致 | P0 |

- **D16**：报名与申请书首次提交在同一报名流程内完成（同一事务）；允许先保存申请书草稿（此时报名记录已创建）。

### 4.15 课题联系方式与入群二维码（课题报名页）

> 定位：在**具体课题的报名页面**上，由管理用户维护该课题的**联系方式**与**入群二维码**，学生报名后即可查看，解决"报名成功却找不到组织"的断层。联系方式是**课题级**数据（不是用户级、不是系统级）。

#### 4.15.1 字段（课题级）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `contact_info` | text | 联系方式文本，支持多行，如导师姓名/邮箱/电话、办公地点、微信号、钉钉号等 |
| `contact_qr_key` | varchar | 入群二维码图片存储 key（对象存储私有桶） |
| `contact_qr_file_name` | varchar | 原始文件名 |
| `contact_qr_file_size` | bigint | 文件大小（字节） |
| `contact_qr_mime_type` | varchar | 图片类型 |
| `contact_visibility` | varchar | `PUBLIC_LOGIN` / `ENROLLED` / `APPROVED`，默认 `ENROLLED`（报名后可见） |
| `contact_updated_at` | datetime | 最近更新时间 |
| `contact_updated_by` | bigint | 最近更新人 |

#### 4.15.2 可见性规则

| 取值 | 含义 | 可见人群 |
| --- | --- | --- |
| `PUBLIC_LOGIN` | 登录可见 | 任意已登录用户（含未报名者） |
| `ENROLLED`（**默认，D1 定稿**） | 报名后可见 | 该课题已有报名记录的学生（含待评审、待定状态） |

- 管理用户 **始终可见**，不受 `contact_visibility` 限制；
- 不满足条件的用户，接口 **不返回任何联系方式数据**（不是前端隐藏），前端展示占位提示；
- 该规则独立于个人主页可见性与报名名单可见性配置（BR-12、BR-26）；
- **已定稿（D1）**：新建课题默认取 `ENROLLED`（报名后可见）；三档机制保留为可配置项，允许课题级覆盖。

## 6. 状态机

### 6.1 课题 Project

```
草稿 ──发布──> 已发布 ──到报名开始──> 报名中 ──到报名截止──> 报名截止
                                       │
                    审核阶段（手工或到点自动）──> 审核中 ──> 进行中 ──> 已完成
任意非终态 ──取消──> 已取消
```

- 状态与时间字段联动：`signup_start` / `signup_end` / `project_start` / `project_end`。
- 自动流转依赖定时任务（P0 可用惰性计算 + 定时任务双保险）。
- **D9**：已发布 = 已发布但未到报名开始；到达 `signup_start` 自动转报名中。

### 6.2 报名 Enrollment

```
PENDING(待评审) ──评审通过──> APPROVED ──> 创建 ProjectMember
       │
       ├──评审待定──> ON_HOLD（保持占用名额，学生端显示"审核中"）
       ├──评审拒绝──> REJECTED（按配置释放名额；释放后至截止前可继续报名）
       └──学生取消──> CANCELLED（释放名额）
```

- **D10**：未开启审核的课题，报名即 `APPROVED` 并创建成员（模块待分配），名额立即占用。
- **D8**：`PENDING` 表示待评审，`ON_HOLD` 表示评审待定，两态学生端均显示"申请审核中"。
- **D11**：候补 `WAITLIST` 本期不实现，从枚举中移除。
- **D12**：拒绝释放名额后，至 `signup_end` 前可继续报名。

### 6.3 申请书 Application

```
DRAFT ──提交──> SUBMITTED ──评审开始──> REVIEWING ──> APPROVED / REJECTED
  ↑                                                        │
  └──── 截止前可修改；截止后 locked_at 锁定（D15：拒绝后亦锁定，不再提交） ──┘
```

### 6.4 任务 Task

```
TODO ──> DOING ──> DONE
  │        │  └──> BLOCKED ──> DOING
  └────────┴──> CANCELLED
进度 0~100；**D14**：置 `DONE` 自动进度 100%，进度设 100% 自动置 `DONE`，均写进度日志
```

### 6.5 成果 Achievement

```
DRAFT ──提交──> PENDING ──审核──> APPROVED（公开）
                          └──> REJECTED ──修改后重新提交──> PENDING
```

### 6.6 成员 ProjectMember

```
ACTIVE ──完成课题──> COMPLETED
   └──退出（本人申请经审核 / 管理用户移除）──> EXITED（记录 exited_at、exit_reason）
```

## 8. API 设计

### 8.1 统一约定

- 协议 HTTPS，数据格式 JSON，接口前缀 `/api/v1`。
- 认证：`Authorization: Bearer <token>`（JWT）。
- 统一响应：

```json
{ "code": 0, "message": "success", "data": {} }
```

- 分页参数：`page`、`page_size`，响应含 `total`、`list`。
- 错误码分段建议：`0` 成功；`1xxxx` 参数/校验；`2xxxx` 认证鉴权；`3xxxx` 业务冲突（满员、重复报名、已截止）；`5xxxx` 系统错误。

Vue 3 + TypeScript、Vite、Vue Router、Pinia、Axios、Element Plus 或 Naive UI、ECharts（看板）、富文本编辑器（TipTap / Quill，用于申请书）、CSS Grid/Flex + 媒体查询做响应式。

### 10.2 后端

Go 1.22+、Gin 或 Echo、GORM、PostgreSQL 或 MySQL、Redis（验证码/缓存/限流/看板缓存）、JWT、bcrypt、邮件服务（仅注册/重置密码验证码，通知类邮件本期不做 D17）、定时任务（逾期提醒、看板预计算、状态自动流转、申请书锁定）、对象存储（简历/附件/成果/二维码）。

**分层**：Controller → Service → Repository；统一异常处理与日志。

### 10.3 部署

Nginx 托管前端静态资源；Go API 独立部署；数据库独立部署；对象存储私有部署；前后端 HTTPS + JSON 通信。

> 说明：本目录 `oa/` 位于招新站仓库内，但 OA 系统是独立应用（不同前端技术约束，不使用 Vapor Mode / anime.js 那一套），需自建 `package.json`、构建配置与后端服务，不与招新站前端构建产物混用。

## 11. 非功能需求

### 11.1 安全

| 编号 | 要求 |
| --- | --- |
| NFR-SEC-01 | 密码 bcrypt 加密存储 |
| NFR-SEC-02 | JWT 设置有效期，支持退出失效 |
| NFR-SEC-03 | 邮箱验证码限制发送频率与校验次数 |
| NFR-SEC-04 | 防 SQL 注入、XSS、CSRF |
| NFR-SEC-05 | 管理接口必须校验角色与数据权限 |
| NFR-SEC-06 | 敏感操作记录日志 |
| NFR-SEC-07 | 简历、申请书附件、成果附件私有存储，下载/预览必须鉴权 |
| NFR-SEC-08 | 申请书内容仅本人与管理用户可见 |
| NFR-SEC-09 | 课题联系方式与入群二维码按可见性鉴权，二维码图片禁止公开直链 |
| NFR-SEC-10 | 管理用户自保护校验（BR-24）在后端强制，不依赖前端置灰 |

### 11.2 性能

- 列表分页查询；课题详情可缓存。
- 看板数据预计算 + 缓存。
- 数据库索引：邮箱、学号、课题状态、报名唯一约束、任务状态、成果状态。
- 报名使用数据库事务 + 行锁或乐观锁，保证不超卖。
- 大附件上传支持分片或直传对象存储。

### 11.3 可用性 / 可维护性 / 兼容性

- 响应式支持 PC 与移动端浏览器；看板图表移动端可读。
- 错误提示友好；操作有明确反馈。
- 接口版本化（`/api/v1`）；前端组件化；统一异常与日志。
- 兼容 Chrome、Edge、Firefox、Safari 等现代浏览器。
